## Why

用户输入「今天走到好的票，放量票找十个给我」，`POST /v1/chat` 返回：

> 对话连接失败（HTTP 400）：未能从消息中识别出股票标的。请输入代码（如 600519.SH）或可识别的公司名称。

三层问题，逐层实测确认：

1. **解析层没错**。这段话里确实没有个股标的，`resolve_symbol` 返回 `(None, ())` —— 不猜标的正是设计要求（猜错标的比问一句糟得多）。实测三种说法（「今天走到好的票，放量票找十个给我」/「帮我找十只放量票」/「今天哪些票在放量」）均为 `(None, ())`。

2. **提示文案归因错误**。400 说的是「请输入代码或可识别的公司名称」，把一个**合法的全市场筛选需求**误报成「你没说清楚」。这是本变更要修的第一件事。

3. **能力存在但没接线**。平台**已有**成熟的全市场扫描器 `api/services/market_scanner_service.py`（816 行，六因子模型 + 8 个评分档案，其中 `breakout` 档的定位就是「量比 + 逼近日高双重确认」），挂在 `POST /v1/recommendations?source_mode=market_scan`。实测（同一账号）：

   ```
   POST /v1/recommendations {top_k:10, source_mode:"market_scan", score_profile:"breakout", scan_limit:800}
   → HTTP 200，61.5s，返回 10 只：002169.SZ 智光电气 / 002180.SZ 奔图科技 / 000823.SZ 超声电子 …
   ```

   「研判对话」是**单标的判定**入口，扫描能力不在它的工具面里 —— Agent 想调也调不到。

## What Changes

1. **新增第 4 类意图：无标的·全市场筛选**（`screen`），与既有的「单标的研判」「组合级研判」「事实型问句」并列。检测是**零 LLM 的纯函数**，与 `RuleTierClassifier` 同层。
2. **新增工具 `market_screen`**，把扫描器接进工具面（`ToolSpec` 单一权威定义），按 `market_scanner_service` 的真实结果产出**逐候选证据**，使「候选来自扫描器」成为可校验的事实而非承诺。
3. **诚实声明**（这是本变更的核心质量要求，不是附属项）：
   - 实测发现 `volume_ratio` 与 `turnover_rate` 在 sina 数据源下为 `null`，即 `breakout` 档名义上「量比确认」实际贡献 **0.0**。用户要「放量票」时**必须声明"量比未提供、放量未经确认"**，不得把「按突破档排序」说成「已确认放量」。
   - 必须声明扫描范围（`pool_size` / `scored_size` / 是否被 `scan_limit` 截断）、数据时点（`quote_time` / `quote_source`）、生效的过滤条件。
   - 扫描实测 61.5s（scan_limit=800），远超中档 30s 目标延迟 —— 必须**在开始前**告知预计耗时，并把「超出档位目标延迟」如实记入回合结果。
4. **修 400 文案分流**：分辨「缺标的」与「这是全市场筛选需求」，后者不再拒绝而是直接执行；前者给出两条可行动路径。

## Non-Goals

- 不做「按财务指标筛选」「多因子自定义选股器 UI」。本次只把**既有扫描能力**接入对话，不新增选股算法。
- 不改变扫描器自身的因子与权重（`market_scanner_service` 逻辑零改动；只在数据缺失时**如实标注**）。
- 不在本轮为候选票顺带跑洗盘探针（用户已明确选择「只给筛选结果 + 依据」）。想深入某只，用户下一轮单独问它。
- 不引入实时推送/后台任务化扫描。本轮是同步调用 + 诚实告知耗时。
