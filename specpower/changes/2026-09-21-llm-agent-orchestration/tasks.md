## 依赖与前置

1. **模型可用性**：规划层需要一次额外 LLM 调用。当前账号的档案均未设为默认（见上一轮记录），Phase 1 上线前需先解决默认模型配置，否则规划层会跟着回答层一起 401。
2. **数据源可用性**：本机 `akshare` 日线取不到（`InsufficientHistory`），涉及行情的黄金集用例只能在数据源恢复的机器上跑分。
3. **产品决策**：`proposal.md` 文末三个问题需先定（异步交付方式、工具权限裁剪、黄金集范围）。

### 仍然存在的最后一环（下一步）

事实型问句现在**能取数了**，但**取到的数还没有证据契约**：19 个数据工具返回的是
vendor 预格式化字符串（`structured=False`），`evidence` 为空。于是校验器正确地
拒绝任何具体数字，回答仍会退化为"无可用证据"。实测 trace：

```

get_zt_pool          ok=True  evidence_count=0     → 降级（unsourced_date）
```

这正是提案里写的"预格式化中文表格无法做数值推理"那条——**L2 证据契约**应作为
Phase 2 的第一项：把数据工具的 vendor 输出转成 `EvidenceItem`（数值 + 单位 + 来源 + as_of），
让"现在多少钱"能真的答出来。这也再次证明 trace 的价值：一条查询就定位到
"工具跑成功但没证据"，而不是靠猜。

## 第 13 轮：三项修复（用户要求"保证确定修复了"）

每项都给出**线上实测证据**，不只是测试变绿。

### ① L2 证据契约：数据工具必须产出可引用证据

**发现**：`get_realtime_quotes` 返回的**本来就是 JSON**，只是没被转成证据——
`evidence=()` 于是校验器正确地拒绝任何数字，回答只能答"无可用证据"。

**实现**：`_evidence_items_from_json`（`tools/data.py`）：JSON 型输出逐字段转
`EvidenceItem`（数值保持 float，配中文标签与单位）；实时类没有日期参数时
从载荷的 `quote_time` 取 `as_of`。**表格/散文型输出不解析**——从文本里抠
"标签=数字"极易错配，错配的证据比没有证据糟得多。证据条数上限 40。

**顺带修掉一个漏网的失败识别**：`get_zt_pool` 在非交易日返回「涨停板情绪池数据
**暂不可用**。」——文案里还带日期，看上去像数据。已把「暂不可用/暂无数据」类
"客气话"补进失败标记（否则一条不可用的返回会被当成有效数据往下走）。

**线上实测**：

```
问：「600519 现在多少钱」→ HTTP 200，10.2s，get_realtime_quotes 证据 11 条
答：「截至2026-09-21 15:34:59，600519.SH 现价为1252.57元，较昨收1257.12元下跌4.55元，
     涨跌幅为-0.3619 pct [E1][E5][E6][E7][E10] - 今开1259.0元，最高1259.95元，最低1250.8元…
     **数据未覆盖**：position」   终态 completed
```

每个数字都带引用——这正是此前答不出来的那句话。新增 `tests/test_data_tool_evidence.py`（9 条）。

### ② 判定链路端到端截止时间

**发现**：实测一次判定**卡 10 分钟没返回**（取数链路每个源都无超时，akshare 内部还重试）。
对投研产品而言「没有结论」必须是一个**能按时给出的结论**——挂在半路比"数据不足"糟得多。

**实现**：`VERDICT_DEADLINE_SECONDS = 60` + `_run_with_deadline`（`signal_service.py`）。
超时抛可读错误（路由转 422），**不等待**卡住的工作线程（`shutdown(wait=False)`）——
与 `ToolRegistry.invoke` 同一取舍。真实异常照常上抛（不把"取数失败"伪装成"超时"）。

**线上实测**：

```
GET /v1/signals/washout?symbol=600519.SH → HTTP 200，20.7s（此前：>10 分钟被强杀）
state=insufficient_evidence  unavailable=['capital_composition','chip_distribution','relative_strength']
```

注意 `intraday_absorption` **已不在未覆盖列表**——上一轮接的新浪分时兜底生效了。
新增 `tests/test_verdict_deadline.py`（4 条）。

### ③ 分时新浪兜底（上一轮已修，本轮验证生效）

见第 12 轮；本轮实测确认 `intraday_absorption` 从 unavailable 中消失。

### 黄金集实测（50 条，真实 LLM 规划器，同一把尺子）

| 指标 | 基线（纯规则） | 规划层接入（未采用 steps） | 规划层（采用 steps） |
|---|---|---|---|

| 澄清正确率 | 66.7% | 97.8% | **97.8%** |
| 工具召回率 | 75.8% | 63.6% | **75.8%** |

**③ 的验收条件（覆盖率与规划准确率显著提升）已达成**：60%→100%、46%→82%。

### 过程中修掉的两个"尺子/接线"错误（都是我自己引入的）

1. **计划里的 steps 被丢弃**：规划层上线后覆盖率大涨，但工具指标**下滑**——因为
   `_plan_tools` 仍按档位机械决定工具。规划层的核心产出（工具选择）没被采用，
   等于只换了个档位。已改为步骤优先、机械规则退居降级路径。
2. **度量口径没读计划**：harness 的意图是从"解析出什么标的"反推的，所以规划层
   上线后规划准确率**纹丝不动**（46%→46%）。尺子本身错了，数字就不会动——
   这正是"先有度量再改行为"的反面教训：**改完行为还要检查尺子是否还量得准**。

### 仍未收口

* **工具精确率 54.4%（基线 86.2%）**：规划器倾向多调工具（例如探针之外再加一个
  数据工具）。两条修法待定：收紧规划提示词要求最小工具集，或校准黄金集的
  `optional_tools`（若多调的那个工具确实提供了有用证据，就不该算噪声）。
* 计划落库的"可重放"只到 trace 记录层面，尚未做到"按计划重跑得到同一路径"的
  自动校验。
