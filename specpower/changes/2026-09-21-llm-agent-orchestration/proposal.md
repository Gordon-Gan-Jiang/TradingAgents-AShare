## Why

用户提出的架构是主流方向，也确实是本平台该走的路：

> 先接入大模型 → 大模型判断是否调用工具 → 工具封装平台能力 → 执行工具 → 结果反喂模型 → 多轮对话

但照搬会**丢掉这个平台真正的护城河**。所以本提案回答两个问题：这个设计合理吗？更好的方案是什么？

### 现状的三条实测证据

**证据 1：意图与标的识别是字面匹配，任意自然语言进不来。** 用真实 3.2 万名称表实测 14 句自然说法，**13 句被 400 挡住**：

| 说法 | 今天的结果 |
|---|---|
| 茅台最近怎么样 | ✅ 单标的（靠中文后缀别名） |
| 宁王还行吗 / 白酒龙头能不能拿 / 那个造电池的股票怎么样 | ❌ 400 |
| 帮我物色几个短线机会 / 有啥能买的 / 哪只票适合抄底 | ❌ 400 |
| 最近资金在往哪走 / 最近哪个板块最强 / 给我讲讲现在市场情绪 | ❌ 400 |
| 今天大盘怎么样 / 我持仓里最危险的是哪只 | ❌ 400 |

原因是 `routing.py` 用关键词表（`_SCREEN_NOUNS`/`_LIGHT_MARKERS`/…）判意图、`resolve_symbol` 用名称字符串判标的，且**无标的的问句只有一个落点**（全市场筛选，还要先过标记词）。

**证据 2：平台能力大量锁在 HTTP 层，工具面极小。**

| 项 | 数量 |
|---|---|
| `api/main.py` 的 HTTP 端点 | **132** |
| `api/services/` 服务模块 | **41** |
| 注册进工具面的 ToolSpec | **19**，且**全是数据型**（`get_stock_data`/`get_fundamentals`/…） |
| 决策型工具 | 2（`signal_washout_probe`、`_batch`）+ 1（`market_screen`，本轮刚接） |

也就是说：自选/跟踪池、持仓与组合、市场主线、平台推荐结果、历史报告与结论、判定兑现与校准、每日操盘与交易计划、数据时效契约——这些**平台独有的能力**，Agent 一个都调不到。用户说"把平台能力原子化封装成 tools"指的就是这块，它是本提案最大的工作量。

**证据 3：今天的"两引擎分流"是被成本逼出来的，不是最优形态。** 轻档 5s/中档 30s/重档 10min 三档由**关键词**机械决定工具计划（`_plan_tools`），LLM 只负责"解释已有证据"，不参与"决定做什么"。好处是可预算、可回测；代价是**必须预先穷举所有问法**——这正是证据 1 里 13/14 失败的根源。关键词表穷举不完自然语言，这条路已经走到头。

### 结论：合理，但要加三处关键修正

| # | 用户的原方案 | 修正 | 理由 |
|---|---|---|---|
| 1 | 大模型判断是否调用工具 | **规则前置 + LLM 兜底**：能确定性判定的走规则（零成本、可穷举），规则不确定或低置信才交 LLM，且 LLM 输出**结构化 Plan**（schema 校验、失败降级） | 高频问句（"是不是在洗盘"占多数）付 LLM 路由成本是纯浪费；而 LLM 路由必须有确定性降级路径，否则分类器一挂整条链路就挂 |
| 2 | 执行工具 → 反喂模型 | 执行放进**确定性信封**：预算/超时/熔断/幂等由代码强制，工具结果**必须变成带编号的证据**再喂模型 | 否则模型"选择性引用"工具结果、或把未取到的数据说成已确认——平台现有的零 LLM 校验器与覆盖声明正是为了堵这个 |
| 3 | 多轮对话 | 多轮要显式**槽位状态**（标的/时间范围/已取证据/未覆盖项/待确认动作）+ 计划落库可重放 | 只把历史消息塞进提示词，等于每轮重新猜指代；而判定落库与校准闭环要求"同一个问题可复现同一条路径" |

**一句话的架构原则**：

> **LLM 决定「做什么」；代码决定「能不能做、做了算不算数」。**

这条原则不是保守，而是这个平台的差异化所在。工具调用循环人人都有；**可回测的确定性判定 + 零 LLM 的引用校验 + 显式弃权 + 判定兑现跟踪**才是护城河。本提案的目标是把 LLM 的能力装进这个信封，而不是换掉信封。

## What Changes

1. **规划层（新）**：`TierClassifier` Protocol 早已为它留好位置（`DegradingClassifier` 就是"包装任意分类器并统一降级"），实现 `LlmPlanner`：输入用户话 + 会话槽位 + 工具清单摘要，输出结构化 `Plan{intent, symbols, horizon, steps[], need_clarify, budget_tier}`。规则前置，LLM 兜底，schema 校验，失败降级到中档 + 追问。
2. **工具面原子化（最大工作量）**：把 41 个服务里的平台独有能力按**决策粒度**封装成 `ToolSpec`（单一权威定义，天然可同时供对话 Agent / MCP / 既有 LangGraph 管道使用）。分三层：
   * **L1 决策工具**（回答"这只票怎么样"）：洗盘判定、组合风险体检、主线判断、报告结论检索、判定兑现查询。数量少、语义强。
   * **L2 证据工具**（回答"凭什么"）：现有 19 个数据工具 + 新闻 + 筹码/分时/资金流。
   * **L3 任务工具**（分钟级，**必须异步**）：全文研报生成（`submit → job_id → poll`）。同步工具面绝不放分钟级管道——MCP 客户端会超时重试。
3. **工具检索（tool search）**：工具变多后，把全部工具塞进提示词会撑爆上下文且降低选择准确率。改为按意图**检索相关工具子集**再注入（L1 全量常驻 + L2 按需检索）。
4. **多轮状态机**：会话槽位 + 证据账本（跨轮累积、标注轮次与 as_of、同 as_of 不重复取数）+ 统一澄清/确认机制。
5. **可观测与评测**：每轮 trace（plan / 每步耗时与结果 / token 与成本 / 判定 / 校验结论）落库；50–100 条真实问句的**黄金集**评测 planning 准确率、工具调用精确率/召回率、弃权正确率。
6. **保持不动的底线**（本提案显式声明）：零 LLM 校验器、覆盖声明、freshness 契约、判定不可被模型覆写、免责与语言护栏、信号层纯函数（AST 测试强制）。

## Non-Goals

- **不引入"模型自由决定一切"的纯 ReAct 循环**：步数不可预知 → 成本方差大、延迟不可承诺、路径不可审计。金融场景要可复现。
- **不让 LLM 生成交易建议或判定**：判定来自确定性信号层；建议来自平台既有推荐服务（Agent 只做**读取与解释**）。
- **不改信号的因子与权重**，不动既有 7 分析师管道（重档仍走 LangGraph）。
- **不做自动交易执行**：动作类工具保持"提议 + 用户确认"（已有 `surface` 区分产品内对话与 MCP 只读）。
- 本提案是**设计**，不含实现。
