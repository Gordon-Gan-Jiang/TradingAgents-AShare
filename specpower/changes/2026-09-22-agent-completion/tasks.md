## 1. 背景与依据（立项时的认知，**其中一行已被证伪**）

实测事实（详见 `docs/agent-status.md` §4）：

| 事实 | 值 | 现在是否仍成立 |
|---|---|---|
| 模型调用占回合延迟 | **93–98%** | ❌ **均值假象**。真实是中位 1.7% / P90 29.6% / 最大 86.4% |
| 单位输出 token 延迟 | **≈ 5 ms/token** | ✅（但含推理 token） |
| 真实使用 15s 内占比 | **34.6%**（中位 26.7 s） | ✅ |
| `max_tokens` | **从未设置** | ✅（且发现它**从未能设置**——白名单漏了） |
| 简单问题输出 token | 1012（→5.3 s） | ✅ |
| 复杂问题输出 token | 2340（→11.6 s） | ✅ |
| 隐藏推理 token | 正文 745 字符，计费输出 2340 token | ✅ |

立项结论是"**延迟 ≈ 输出 token × 5 ms**，所以第一优先是约束输出长度"。
**这个结论错了**：见 §3 的三条否证。

## 2. 工作流 A · 延迟 —— **三条假设全部实测否掉**

| # | 任务 | 原定验收 | 实测结果 |
|---|---|---|---|
| A1 | 对话路径显式设置 `max_tokens` | 值确实传到客户端；病态回合被截到上限 | ⚠️ **保留接线修复，默认不设**。该 provider 的 `max_tokens` **只约束可见输出，不约束推理 token**——从"不设"压到 1024，延迟与 token 都没变 |
| A2 | 提示词瘦身：约束 `claims` 条数与长度 | 同类问题输出 token 下降 | ❌ **回退**。实测输出**更多**（1654 vs 1445）、延迟**更差 21%**（8278 vs 6842 ms） |
| A3 | repair 条件化：不可修的失败不再发起第二次调用 | 不可修 → 0 次 repair | ❌ **不做**。实测 repair **有效 64%**（28 次触发修回 18 次），条件化会丢掉这些 |
| A4 | 归因度量：token 拆分 | trace 可查拆分 | ➡️ **合并进 D**（归因端点） |

**A3 的否证尤其值得记**：立项时假设"不可修的失败不该重试"，实测发现
**大多数可修**——真问题是另一头（轻档预算 1 次 = 永不修复，见
`docs/agent-status.md` §4.5）。

### 本工作流真正的产出

1. **一个真 bug（已修）**：`OpenAIClient.get_llm()` 的透传白名单漏了 `max_tokens`，
   调用方传了会被**静默丢弃**。
2. **三条否证 + 方法教训**：本路径方差 2.4 倍，**单次采样不能作为结论**。
3. **优先级更正**：延迟是双峰的，P90 那一段要靠**工具侧**限时/缓存（见 §4.6）。

## 3. 工作流 A 的实测明细（否证的依据）

| 假设 | 对照 | 结果 |
|---|---|---|
| `max_tokens` 封顶 → 变快 | 不设 2746 token / 11.4 s；**1024** 仍 2620 token / 12.0 s | ❌ 无效 |
| 提示词简洁 → 变快 | 有规则 1654 token / **8278 ms**；无规则 1445 token / **6842 ms** | ❌ 更差 21% |
| `reasoning_effort` 调低 → 变快 | minimal 11138 / None 13211 / low 14254 ms | ❌ 分不开 |

**方差（同一配置重复三次）**：8.4 s / 13.2 s / 19.8 s。
**结论**：瓶颈是**服务端推理 token**，上述参数一概管不到。

## 4. 工作流 B · 确定性：毛利率的真相

> **本轮更正上一轮结论**：`HANDOFF.md` §12.3 记为"财务比率没有确定性落点，需补 L1 纯函数"。
> 实测**推翻该前提**——`get_fundamentals` 已经返回毛利率/ROE/资产负债率/销售净利率/ROA，
> 问题在**路由**与**单位**。

| # | 任务 | 验收 |
|---|---|---|
| B1 | 路由修正：「毛利率/净利率/ROE/资产负债率」→ `get_fundamentals`（而非 `get_income_statement`） | 单测：问句路由到正确工具；**端到端**：问「600519 的毛利率是多少」得到带引用的比率，不再降级 |
| B2 | 单位修正：比率类字段的 `unit` 从 `yuan` 改为 `pct` | 单测：`毛利率（…）` 的 unit 是 `pct`，`营业收入（…）` 仍是 `yuan` |

**B2 的判据**：按**字段名**判断，不按工具。含「率」「比率」「占比」→ `pct`；
货币词（收入/成本/利润/资产/负债/现金流/权益/每股）→ `yuan`；都不匹配 → `""`（留空）。

**为什么 B2 不是纯美化**：提示词会把 unit 渲染给模型
（`毛利率（2026-06-30） = 89.5552 (yuan, 截至 …)`），标错单位会误导模型
写成「89.5552 元」。`EvidenceItem.is_numeric` 也依赖 `unit ∈ NUMERIC_UNITS`。

## 5. 工作流 C · 韧性（Phase 2.5 残留）—— **实测后判定不做**

| # | 任务 | 结论 |
|---|---|---|
| C1 | 同回合内同工具同参**结果复用** | ❌ **不做**：无可去重对象 |
| C2 | 供应商**连续失败熔断** | ❌ **不做**：无可短路对象 |

**依据（实测 611 个含工具步骤的回合）**：

    同工具被调用多次的回合：**0**（0.0%）
    同工具同参数重复调用的回合：**0**

计划里的理由原文是"东财系封禁下，4 个板块工具每轮都真失败并重试，白付延迟"。
实测**该描述不成立**：工具在一轮里**从不重复调用**（规划层已去重），
所以既没有重复取数可复用，也没有连续失败可熔断——两者都会是死代码。

跨回合的熔断确实有意义（供应商持续故障时少付延迟），但那需要引入**跨请求的
共享可变状态**，并承担"供应商已恢复却仍被熔断"的风险。在没有实测收益前不引入。

**教训**：这条是"计划里写得像真问题、实测后不成立"的例子。计划的措辞
（"每轮都真失败并重试"）来自对封禁现象的推断，而不是对 trace 的统计。
**凡是能用 trace 数出来的，就不该用推断写进计划。**

## 6. 工作流 D · 观测

| # | 任务 | 验收 | 结果 |
|---|---|---|---|
| D1 | 延迟/成本归因端点：按档位/工具给出中位/P90 与失败率 | 端点返回结构断言 + 真实数据可查 | ✅ `85b56d0` |

**只读端点，不改写任何行为**——观测与行为分开，才能拿它当"改行为"的证据。

**它上线当天就推翻了本轮立项的依据**（见 §1）：第一次能按工具看耗时，
才发现"工具只占 4.5%"是均值假象，真实分布是中位 1.7% / P90 29.6% / 最大 86.4%。

**实现要点**：聚合拆成纯函数 `_summarize_rows`（IO 外壳 `_load_rows`），
边界情况（空历史、全失败、长尾）才测得了。路由声明顺序
（`summary` 必须在 `{trace_id}` 之前）本身也有测试锁住——顺序反了端点会
永远返回「trace 不存在」且不报错。

## 7. 工作流 E · 中档事实问句（**计划外发现**）

| # | 任务 | 验收 | 结果 |
|---|---|---|---|
| E1 | 中档事实问句：具体规则命中优先于判定探针 | 计划层面断言"该留的留、该让的让" | ✅ `8f60eef` |

**怎么发现的**：修完验收集的两条错误期望后，新加的「资产负债表怎么样」
仍然失败——执行的是 `signal_washout_probe`。追下去发现
`plan_factual_tool` **只在轻档被查询**，所以任何被分到中档的事实问句
都在用"洗盘还是派发"回答一个不同的问题（实测「多视角共识怎么样」本应走
`report_consensus_read`）。

**安全前提**（否则会把对的换成错的）：只在**具体命中**时改写；
`plan_factual_tool` 对匹配不上的问句返回通用兜底，
「600519 是不是在洗盘」正是这一类 → **探针必须保留**。实测两类判然分开，
判据因此是明确的，并有专门测试锁住。
