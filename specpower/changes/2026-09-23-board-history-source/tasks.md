# 板块历史数据源可行性调查（2026-09-23）

## 0. 为什么查这个

上一轮修好了主线 T+1 闭环的三个缺陷（缓存 TTL / 静默失败 / 上界写死），
`mainline_t1_outcomes` 从 **0 行 → 34 行**，闭环真的在产出了。

但 34 行里 **33 行是 `数据不足` / `notes=板块历史不可用`**：闭环通了，
却拿不到能算超额收益的**板块**数据。本文件查的是"有没有替代源"。

用户选择：**先找替代源验证可行性**。

---

## 1. 数据需求（比想象的小）

T+1 兑现判定只需要**两个数据点**：

    board_close(trade_date) 和 board_close(check_date)  →  算板块前瞻收益

**不需要完整历史**。这个认识很重要：它把"替代源"的门槛从"有 N 年日K"
降到了"能取到两个日期的收盘"。

判据（`mainline_service.evaluate_t1_for_report`）：

    excess_ret = board_fwd_ret - benchmark_fwd_ret
    outcome    = 兑现 / 证伪 / 走平(跑输基准) / 弱兑现(抗跌) / 数据不足

其中**基准**已修好（沪深300 缓存新鲜到 2026-09-22）。

## 2. 候选源逐个实测（只读探测）

| 数据源 | 函数 | 能取到数据？ | 数据新鲜？ | 结论 |
|---|---|---|---|---|
| **东财板块**（现有主源） | `stock_board_industry_hist_em` | ❌ `ConnectionError: RemoteDisconnected` | — | **死** |
| **同花顺板块指数**（现有兜底） | `stock_board_industry_index_ths` | ✓ 能取 | ❌ **末日 2024-01-08**（停更 2.5 年） | **死** |
| **申万行业指数** | `index_hist_sw(symbol=code)` | ✓ **3046 行 / 0.5s** | ✓ **末日 2026-09-21** | **数据可用** |
| 新浪行业 | `stock_sector_spot` | ✓ 49 行 | ✓ 仅**当日快照**，无历史 | 无法回溯 |
| 东财板块指数代码走指数通道 | `stock_zh_index_daily_em(symbol="BK0478")` | ⚠ 返回 **0 行** | — | 无效 |
| 中证指数 | `csindex` 接口 | ❌ `{"code":"500","msg":"服务器异常"}` | — | 不可用 |

### 2.1 东财是**真封禁**，不是限流

加 2 秒间隔单次调用仍 `RemoteDisconnected` → IP 级封禁，重试无用。

注意区分：东财的**指数**通道与**板块**通道表现不同（`stock_zh_index_daily_em`
一度能取到沪深300），被封的是**板块**类接口。

### 2.2 同花顺兜底**方向就是错的**

`_board_hist_close` 的兜底顺序是"东财 → 同花顺板块指数"。但第二个源
**数据停更于 2024-01**，而代码里已有新鲜度检查（`_fresh()`：末日期距 check_date
超过 15 自然日即返回 None）——所以它会**诚实地返回 None**，不会造假。
这部分设计是对的，问题只在"两个源都不可用"。

### 2.3 申万是唯一活着的源

    index_hist_sw(symbol="801765", period="day")  →  1152 行，末日 2026-09-21，0.5s

抽查 9 个候选代码：**7 个有新鲜数据**。但发现两个不一致：

| 代码 | 我标注的名称 | 行数 | 末日 |
|---|---|---|---|
| 801760 | 传媒(二级) | 3046 | 2026-09-21 ✓ |
| 801765 | 影视院线(三级) | 1152 | 2026-09-21 ✓ |
| 801780 | 白酒Ⅲ(三级) | 3046 | 2026-09-21 ✓ |
| 801010 | 农林牧渔(一级) | 6460 | 2026-09-21 ✓ |
| **801011** | 种植业(二级) | 171 | **2024-06-17 ⚠ 陈旧** |
| **801768** | 游戏Ⅲ(三级) | — | **KeyError ❌ 无此代码** |

## 3. **决定性问题**：名称→代码映射没有任何可用来源

`index_hist_sw` 只返回 **代码 + 价格**，**不返回名称**。上表里"影视院线"之类的
标签是我凭公开知识**猜的**，**没有任何权威来源确认 801765 就是影视院线**。

而报告里用的板块名是**东财名**（`影视院线`、`文化传媒`、`游戏`、`种植业与林业`…），
共 **123 个不同名称**。要用申万，必须先有"东财名 → 申万代码"的映射表。

尝试过的枚举途径全部失败：

| 途径 | 结果 |
|---|---|
| `ak.sw_index_first_info()` | ✓ 仅 **31 个一级**（够粗，不够用） |
| `ak.sw_index_second_info()` | ❌ `AttributeError`（抓 `legulegu.com` 改版了） |
| `ak.sw_index_third_info()` | ❌ `AttributeError`（同上） |
| 直接抓 `legulegu.com/stockdata/sw-industry-overview` | ❌ **HTTP 504**（站点本身故障） |
| `ak.sw_index_third_cons(symbol="801765")` | ❌ `ValueError: No tables found` |
| 申万官网 `swsresearch.com` | ❌ `SSLError` |
| akshare 源码内置静态表 | ❌ 源码里 0 个 6 位代码 |

**结论：本环境下没有任何程序化途径能拿到"申万代码 ↔ 名称"的权威对应关系。**

---

## 4. 为什么不硬编码一张映射表（**这是本文件的重点**）

技术上做得到：申万代码是公开知识，可以手写一张 123 条的表。**但不该做**，理由三条：

### 4.1 猜错会产生"自信的错误判定"

如果 801765 实际不是影视院线，那么 T+1 会拿报告说的"影视院线"去比
**一个完全不相干的行业**。算出来的 `excess_ret`、`outcome=兑现/证伪`
**格式完全合法、看起来毫无异常**。

**这正是本轮用户要我修的"度量会骗人"**：一个测的东西和声称测的东西不一致的指标，
比没有指标更危险——它会让人相信一个假的结论。

### 4.2 粒度粗化会让判定**变成另一个命题**

报告说的是"**影视院线**会上涨"，如果只能映射到申万一级"**传媒**"，
那测的是"传媒板块涨没涨"——**一个更宽、更容易命中、且不同的命题**。
命中率会**虚高**，而这恰恰是"命中率"这个指标最不该有的性质。

### 4.3 覆盖率不完整会重新引入静默失败

实测 801011 停在 2024-06、801768 直接不存在 → 即使映射表正确，
覆盖也是**部分**的。部分覆盖 + 悄然回退，就是本轮刚修掉的
"静默失败"那类病（`数据不足` 会重新变得不可归因）。

## 5. 可行路径（按推荐度排序）

### 5.0 先说一条被否掉的：东财 spot 快照也不可用

曾考虑"每天快照一次东财板块 spot，自己积累出前瞻窗口"（不需要历史），
**实测否掉**——东财 **整个 `_em` 族**都被封：

| 函数 | 结果 |
|---|---|
| `stock_board_industry_spot_em`（板块快照） | ❌ `RemoteDisconnected` |
| `stock_board_industry_name_em`（板块名录） | ❌ `RemoteDisconnected` |
| `stock_board_concept_name_em` | ❌ `RemoteDisconnected` |
| `stock_zh_a_spot_em`（**个股**快照） | ❌ `RemoteDisconnected` |

不只是板块，**连个股快照都不通**。所以"自己攒快照"这条路在当前网络环境下走不通。
（这也解释了为什么工具层有 4–5 个东财系工具是**真故障**。）

### 5.1 剩下的路径

| 方案 | 成本 | 语义保真 | 评价 |
|---|---|---|---|
| **B. 找权威申万代码表**（官网/付费数据/公开 CSV） | 低-中 | 高（三级粒度够细） | **唯一推荐**。拿到权威表后本条路的**数据端已验证可用**（§2.3） |
| C. 换判定口径（只用基准，不用板块） | 低 | **低**（改变命题） | 不推荐默认启用；若启用必须**改口径标签**，不能让"超额收益"这四个字继续用 |
| D. 硬编码映射表 | 中 | **未知（可能错）** | ❌ **不做**，理由见 §4 |
| ~~A. 每日快照东财 spot~~ | — | — | ❌ **已实测否掉**（见 §5.0） |

## 6. 本轮不改代码的理由

`_board_hist_close` 现有行为是**正确的**：两个源都不可用时返回 `None`，
上层写 `outcome=数据不足` / `notes=板块历史不可用`。

**这是诚实降级，不是缺陷**。本轮修的三个缺陷是"把可用数据用错/用丢"，
而这里是"确实没有数据"——两者的正确处置不同：
前者要修，后者要**如实报告并等待数据源**。

所以本文件**只交付调查结论，不改代码**。

## 8. 一句话结论

**数据端可行（申万 `index_hist_sw` 新鲜、快、三级粒度对得上），
卡在"名称→代码"映射没有任何权威来源；而东财整个 `_em` 族被封，
"自己攒快照"这条退路也已实测否掉。**

在拿到权威映射表之前，闭环产出的 `数据不足` 是**正确且诚实**的状态，
**不应通过猜映射或降级口径去"消灭"它**。

## 9. 给下一步的具体建议

1. **要用的那件事**：帮我拿到一张**权威的申万代码↔名称对照表**
   （申万官网导出 / 付费数据源 / 任何可信 CSV 都行）。有了它，
   §2.3 已验证的数据端可以直接接上，改动很小。
2. **网络环境**：东财 IP 级封禁影响的不只是这条闭环——工具层 4–5 个东财系
   工具是同样的真故障。换出口（代理/换机器/换网络）能一次性解决一整批问题，
   性价比可能高于逐个找替代源。
3. **不要做的事**：不要为了"让指标好看"而把板块口径降到一级，
   或用手写映射表——那会让"命中率"这个指标失去意义。
