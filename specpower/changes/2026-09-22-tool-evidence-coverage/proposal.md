## Why

对话 Agent 当前有**两条独立的失败链**，本轮已把其中一条（接地校验）修掉，本文档处理另一条：
**工具跑成功了，却产出 0 条可引用证据**，于是回答退化成「本轮无可用证据」。

这不是"偶尔查不到"，而是**设计导致的必然**：`ToolSpec.output_contract = "DATA_PROSE"` 的工具
按约定 `evidence=()`——代码注释里写得很清楚：

> JSON 型输出转成可引用证据；失败文案一律不产出证据（里面即使有数字也不是事实）。
> **表格/散文型输出保持空证据——诚实优先于覆盖率。**
> —— `tradingagents/tools/data.py`，vendor handler

"诚实优先于覆盖率"在当时是对的（宁可不说，不要编）。但它有一个未兑现的前提：**模型看不见的
数字，它只能编**。于是"不产出证据"并不等于"不回答"，而是等于把这一回合推给校验器去拒——
最终用户看到的是弃权或降级，而不是"这个工具查不到"。

### 实测证据（生产库 `tradingagents.db`，2026-09-22，116 轮真实对话）

回答形态的真实分布：

| 形态 | 条数 | 占比 |
|---|---|---|
| 有实质回答（completed + content） | 44 | 37.9% |
| **空转弃权**（completed 但正文是「本轮无可用证据」） | 25 | 21.6% |
| degraded（有内容但被校验器拒收） | 47 | 40.5% |

**证据 1：34/116 条 trace 的证据总数为 0。**

逐 trace 统计 `chat_turn_traces.steps` 的 `evidence_count`：

| 类别 | 条数 |
|---|---|
| 有证据 | 81 |
| **零证据** | **34** |
| 未调用任何工具 | 1 |

零证据的 34 条中，只有 **8 条**能归因到参数错误（`unknown arguments` 等）。其余 **26 条是
"工具 `ok=true` 但产出 0 条可引用证据"**——失败了却报告成功。

**证据 2：白跑的工具清单（26 次，按次聚合）。**

| 工具 | 白跑次数 | 实探的返回形状 |
|---|---|---|
| `announcements_read` | 4 | 结构化，但该标的确实无公告 |
| `trade_ledger_read` | 3 | **读空表**（`trade_ledger` 0 行） |
| `verdict_outcome_lookup` | 3 | **读空表**（`signal_verdict_outcomes` 0 行） |
| `get_fundamentals` | 2 | **Markdown 表格** |
| `get_balance_sheet` | 2 | **Markdown 表格** |
| `get_income_statement` | 2 | **Markdown 表格** |
| `get_zt_pool` | 2 | 半结构化文本（`2026-09-21 涨停家数：103`） |
| `get_global_news` | 2 | **失败文案**：`Error fetching global news: Too Many Requests. Rate limited.` |
| `get_hot_stocks_xq` | 2 | 表格/文本 |
| `get_board_fund_flow` | 2 | 表格/文本 |
| `get_board_spot` | 1 | 表格/文本 |
| `get_board_rank` | 1 | 文本 |

**关键交叉验证**：这 26 次白跑里，**没有一次**来自本轮已退役的 8 个工具。退役那 8 个
（`get_stock_data`/`get_cashflow`/…）规划器本来就不选，所以**退役不改善空转率**——
它是"缩小误选面"，与本提案是两件事。

**证据 3：`_looks_like_vendor_failure` 的失败识别不全（诚实性 bug）。**

实探 `get_global_news` 返回：

```
Error fetching global news: Too Many Requests. Rate limited. Try after a while.
```

`_VENDOR_FAILURE_MARKERS`（`data.py:484`）覆盖了 `获取失败` / `暂不可用` / `temporarily
unavailable` 等，但**没有 `Error fetching`、没有限流措辞**。后果不是"少一条证据"，而是
**真实的数据源故障被静默表述成"没有数据"**——用户看到「本轮无可用证据」，看不到
"数据源被限流了"。这违反了平台自己声明的口径（`_coverage_for` 的注释：vendor 失败时
不得声称该源可用）。

**证据 4：白跑的工具会被规划器反复选中。** 上表中 `get_fundamentals` / `get_balance_sheet`
等正是 `routing.py` 的 `FACTUAL_TOOL_HINTS` 明确定向的工具（"市盈率/市净率/估值" →
`get_fundamentals`）。也就是说：**问"茅台市盈率多少"，规划器一定会选一个必定产出 0 证据的工具**。
这不是偶发，是可复现的必然。

## What Changes

核心约束：**不得改变 vendor 已渲染的字符串**。分析图（7 分析师管道）要求逐字一致
（`tests/test_data_tools_migration.py` 的模块 docstring：边界是"不改变既有分析图的行为，
工具名与返回的字符串必须逐字一致"）。因此证据必须**从既有渲染结果里派生**，而不是
改上游返回形态。

| # | 改动 | 说明 |
|---|---|---|
| 1 | **表格 → 证据解析器** | 新增 `_evidence_items_from_table(rendered, ...)`：解析 Markdown 表格的表头与数据行，产出 `EvidenceItem`。数值**逐字取自文本**（不换算、不推断），因此不可能编造。覆盖 `get_fundamentals` / `get_balance_sheet` / `get_income_statement` / `get_board_*` 等表格型输出 |
| 2 | **半结构化文本解析器** | `get_zt_pool` 这类"键值 + 简单列表"的固定格式，写定向解析（`涨停家数：103` → `EvidenceItem(field="涨停家数", value=103)`）。**只在格式匹配时产出**，不匹配就保持空证据 |
| 3 | **补齐失败识别** | `_VENDOR_FAILURE_MARKERS` 增加英文错误与限流措辞（`Error fetching`、`Rate limited`、`Too Many Requests` 等）。识别为失败后走既有的 `degraded=True` 路径，让「数据源故障」如实出现在回答里，而不是伪装成"没有数据" |
| 4 | **读空表的工具如实说明** | `trade_ledger_read` / `verdict_outcome_lookup` 读的是 0 行表。它们不该表现成"查了但没有"——应显式声明"该能力尚无数据"（前者取决于持仓数据是否接入，见 Open Questions） |
| 5 | **把口径变成会失败的测试** | 为每个新增解析器补测试；并为"表格型工具不得产出空证据"补一条护栏测试（用真实 vendor 文案做 fixture），让这类回归必然失败 |

### ⚠️ 与既有决定冲突：表格解析是**被明确拒绝过**的

`_evidence_items_from_json` 的 docstring（`data.py:314`）写着：

> 为什么只认 JSON：…**表格不做解析**——从散文里抠"标签=数字"极易错配，
> 而**错配的证据比没有证据糟得多**（校验器的全部意义就是不让错的东西出去）。

上面表格里的改动 #1 正是在推翻它，所以**必须先解决这个冲突**，不能当实现细节处理。
原作者的顾虑站得住：错配的证据会被校验器**接受**（数字确实出现在所引证据里），
这是比弃权更隐蔽的正确性漏洞。

但那份顾虑针对的是「从**散文**里抠标签=数字」。本轮实测了这两张表的规整程度：

| 工具 | 表格行数 | 列数分布 | **列数不一致的行** |
|---|---|---|---|
| `get_fundamentals` | 22 | 全部 10 列 | **0** |
| `get_balance_sheet` | 14 | 全部 18 列 | **0** |

两者都是**严格 Markdown 表格**（含分隔行、列数逐行一致）。也就是说错配**在机械上可防**，
这与"从散文里抠"是两回事。据此把改动 #1 收紧为**带护栏的解析**：

| 护栏 | 规则 |
|---|---|
| G1 规整性 | 必须是含分隔行的 Markdown 表格，且**所有行列表数一致**；任一行不一致 → **整张表放弃**，保持空证据 |
| G2 空值 | `nan` / 空单元格**不产出证据**（`nan` 不是事实） |
| G3 逐字搬运 | 字段名与数值只从表头/单元格**原样搬运**，不做换算、不做推断 |
| G4 时点 | 财务数据的 `as_of` 取**报告期**（表头 `20260630`），不是查询日；取不到合法日期就不产出该行证据 |
| G5 上限 | 受 `_MAX_EVIDENCE_ITEMS` 约束，且单表只取语义最关键的部分（见 Open Question 2） |

另外两处实测陷阱必须一并处理，否则"修好了空证据、引入了新降级"：
**科学计数法**（`4.45169e+10`——模型若写成「445.17 亿」仍会 `unsourced_number`，因此证据值
要规范化到可比较的形态）与 **`nan` 单元格**（见 G2）。

## Non-Goals

- **不改 `tradingagents/agents/utils/*` 的 8+ 个 `@tool`**，不改 `route_to_vendor`，不改任何
  vendor 的返回字符串——分析图逐字一致性是硬边界。
- **不退役更多工具**。退役 8 个已完成（工具面 50 → 42）；本提案是"让留下的工具真能产出证据"，
  与之正交。不把 `get_fundamentals` 这类摘掉——它是"市盈率"类问句的唯一落点，摘掉就从
  "白跑"变成"根本没有工具"。
- **不放松校验器**。产出证据不等于通过校验：数值与日期照旧逐条核对。
- **不新增数据源**。只用平台已经在调的那些 vendor。

## Open Questions（需产品决策）

1. **`trade_ledger_read` / `verdict_outcome_lookup` 怎么处理？** 它们读的两张表都是 0 行：
   前者依赖持仓/成交流水是否接入（当前阻塞在用户侧数据），后者依赖判定兑现是否开始记录。
   可选项：(a) 暂留并让它们显式声明"尚未开始记录"；(b) 先从工具面摘掉，避免必然白跑。
2. **表格解析的证据条数上限**。`_MAX_EVIDENCE_ITEMS = 40` 是提示词容量的保护。财务报表
   一张表可能有几十列 × 多期，全量转证据会把提示词撑爆并拖慢作答（延迟正是要压的目标）。
   取多少？建议"每个工具只取其语义最关键的若干行/列"，但阈值需产品确认。
3. **是否顺带把 `DATA_PROSE` 这个契约细化**。目前 19 个工具共用 `"DATA_PROSE"` 一个值，
   无法区分"表格可解析"与"真散文不可解析"。是否引入 `DATA_TABLE` 等更细的契约值？
